# 班集 · 班级共建站

一个面向大学生的班级服务网页，覆盖互助信息、任务组队、共享资料、截止提醒、匿名意见和竞选承诺展示。

## 账号与登录

- 用户只需要输入账号名称和密码，不需要填写邮箱。
- 网站不请求 Supabase；账号和班级内容使用不需要注册的 MantleDB 公共存储接口。
  （仓库 `legacy/supabase/` 里留着一份早期设计过的 Supabase 建表 + RLS 脚本，当前代码完全没有引用，
  只作为将来迁移的参考，不要在“现在正在跑什么”的意义上读它。）
- 账号名称在班级共享数据库中不能重复（校验是“先查后写”，不是原子操作）。
- 密码使用 Web Crypto PBKDF2 加盐后保存，网站不会保存明文密码。
- 登录会话保存在当前浏览器中，刷新或重新打开网站后会自动识别；只有主动退出登录后才需要重新输入。
- 不同账号在同一浏览器中使用独立的数据空间。

## 身份系统

注册和编辑资料时可以设置班级身份，成员目录会按照“教师与辅导员、班级委员会、普通同学”分组展示：

- 教师与辅导员：任课老师、班主任、辅导员。
- 班级委员会：班长、副班长、团支书、学习、生活、体育、文艺、心理、宣传、组织、纪律和劳动委员。
- 普通同学：默认身份。

教师和班委身份需要管理员审核。普通用户提交申请后仍保持普通同学权限，只有管理员审核通过后身份才会生效。

界面会根据身份分组呈现不同风格：

- 普通同学使用基础班级服务界面。
- 班委使用蓝色工作台主题，并显示任务、日程和成员入口。
- 教师与辅导员使用暖色工作台主题。
- 管理员使用红色管理主题，并显示身份审核与历史记录入口。

竞选栏目只对 `config.js` 中 `campaignUsernames` 指定的作品作者开放。当前仅“刘凯翔”账号可以进入竞选页，其他用户即使手动输入地址也会被重定向到个人中心。

## 发布额度与管理员

- 每个账号每天最多发布 10 条，互助、组队、意见和截止事项均包含在内。
- 同一类型每天最多发布 5 条。额度记在共享数据库而不是浏览器里，所以清缓存不会重置；
  但**它只是防手滑，不是防恶意**，服务端没有任何强制（见下面「安全边界与已知限制」）。
- 用户可以在“个人中心”查看自己的身份、发布记录与今日剩余额度。
- 界面上只能删除自己发布的内容；同样只是前端校验。
- 配置文件中的管理员账号拥有全部权限，包括身份审核、任务与日程发布、删除任意内容和删除历史记录。当前管理员账号为“刘凯翔”。

## 分班级管理

- 注册时必须填写班级编码，账号会绑定到对应班级。
- 互助信息、任务组队、匿名意见、截止事项、成员目录、班级动态和历史记录都按班级隔离。
- 默认班级编码为 `AHU-IC-2026`，现有账号和旧数据会自动归入默认班级。
- 管理员可以在“班级管理”中创建新班级并切换进入。
- 教师和辅导员可以进入自己所属的班级进行管理。
- 普通同学不会看到“班级管理”入口。注意：数据是取回后在浏览器里按班级过滤的，
  这**不等于**服务端做了隔离（见下面「安全边界与已知限制」）。

## 个人课表

- 每个账号拥有独立的个人课表，数据保存在共享数据库的 `schedules/<userId>` 路径。
- 个人中心支持按周查看、上一周、下一周、手动添加课程和删除课程。
- 教务系统的 `idToken` 只在一次性导入时使用，不会写入网页或共享数据库。
- 个人中心可以粘贴安徽大学课表网址，网站会自动识别并生成一段“更新代码”。
- 更新代码需要在安徽大学课表页面执行一次。它会读取当前页面令牌、同步课程，并立即关闭，不会保存令牌。
- ⚠️ **安全提示**：这段更新代码是从本站（`lkx478482771-star.github.io`）加载一个远程脚本后，
  在**安徽大学教务页面**里执行的。它本身只把令牌发回 `jwapp.ahu.edu.cn`，不会外传；
  但它意味着教务页面里运行着本站托管的代码——一旦本站仓库被接管或被改，令牌就有被窃取的可能。
  介意这一点的话可以用「手动添加课程」自己录入，不要执行更新代码。我们正在把它改成不引用任何远程脚本的内联版本。
  （另外课表是写进公共命名空间的，知道你的 `userId` 就能读到你的课表。）
- 自动更新开关开启后，课表超过 24 小时没有更新时，个人中心会显示更新提醒。

## 事项保留与历史记录

- 任务、组队和日程由班委、教师、辅导员或管理员发布，普通同学没有发布权限。
- 发布者可以选择保留 `6、12、24、48` 小时，最长不超过 48 小时。
- 到期后事项自动从当前栏目移除，并归档到“历史记录”页面。
- 管理员可以从历史记录中永久删除归档内容。

## 开发与检查

这个仓库是**零构建**的纯静态站点：没有打包、没有依赖、改完直接刷新。但有几个脚本负责守住“不让明显错误上线”：

```powershell
node scripts/check-icons.mjs    # 源码里用到的每个图标都必须已打包进 assets/icons.js
node scripts/check-size.mjs     # 体积预算（首屏 ≤ 580 KB，单文件各有上限）
node scripts/check-cjk.cjs      # 中文标识符（防止字符串漏引号）
node scripts/check-sync.cjs     # 增量同步 / 限流冷却 / 轮询节奏的回归测试
node scripts/check-budget.cjs   # 「每个命名空间 100 条」的容量预算（按 40 人规模推算）
node scripts/check-backend.cjs  # 后端接缝：MantleDB / Supabase 两套 provider 的 URL 契约与错误语义
node scripts/verify-icons.mjs   # 用最小 DOM 桩验证图标垫片真能渲染出 SVG
node scripts/build-icons.mjs    # 新增图标后重新生成 assets/icons.js（需联网下载 lucide）
python scripts/optimize-hero-image.py .   # 首图重新缩放 + 重压（跳过已压缩过的版本）
```

`assets/icons.js` 由 `scripts/build-icons.mjs` 生成、**不要手改**。它只打包站点真正用到的图标
（当前 93 个），替代了原先 358 KB 的 lucide 全量包（1743 个图标）——现在约 31 KB。
新增图标后忘记重新生成时，`check-icons.mjs` 会在 CI 里直接失败，页面控制台也会给出警告。
`.github/workflows/ci.yml` 会在 push / PR 时自动跑上面的语法检查、图标一致性和体积预算。

## 数据模式

当前版本使用轻量共享模式，请先看清「哪些在云端、哪些只在本机」：

- **在共享存储里（现在是 MantleDB：公开可读、任何人可写）**：账号记录（含加盐口令摘要）、班级、
  互助 / 组队 / 意见 / 截止事项、个人课表、发布额度计数、成员身份与审核状态、运动会照片。
- **只在这台设备上**：登录会话、上传的文件（IndexedDB）、界面缓存与待发送队列。
- 两套后端共用同一份数据模型（`分片名 + path → 一段 JSON`），换后端只换适配器：
  `provider: "mantle"`（现状）↔ `provider: "supabase"`，详见下面的「迁移到 Supabase」。
- MantleDB 是无账号的公共原型服务：没有备份、没有审计、没有限流、没有 SLA，
  命名空间一旦泄漏即可被任意读写。
- 因此**不要**在这里存身份证号、学号、手机号、住址一类信息。
- 长期稳定运营或要处理班级隐私数据时，请迁移到真正的后端：Supabase 这条路仓库里已经铺好
  （见「迁移到 Supabase」），`legacy/supabase/` 是更早一版只有单一 records 表的建表语句，仅作参考。

### 存储分片（免费档 100 条 / 10000 次请求的硬顶）

MantleDB 免费命名空间有三条硬限制（2026-10 实测）：每个命名空间**最多 100 条** entry
（第 101 条**新路径**返回 `403 {"error":"Entry limit reached"}`，覆盖已有路径不受限）、
每条最大 64 KB、每 24 小时最多 10000 次请求（超出返回 429，客户端会静默 10 分钟）。
一个班 40 个人，光「40 个账号 + 40 份课表 + 每天一份额度」就轻松破百，所以数据按前缀分到
5 个命名空间（分片表在 `config.js` 的 `mantleNamespaceMap`，路由见 app.js 的 `mantleNamespaceForPath`）：

| 命名空间后缀 | 装的路径 | 40 人时占用 | 说明 |
| --- | --- | --- | --- |
| `ic-…`（主片） | `accounts/` `classes/` `meta/` | 44 / 100 | 最先到顶，约 91 人时满 |
| `user-…` | `schedules/` | 40 / 100 | 每人 1 条 |
| `usage-…` | `usage/` | 40 / 100 | 每人 1 条（日期写在内容里，不再进路径） |
| `live-…` | `records/` `history/` | 90 / 100 | 归档只留最近 30 条，由 `pruneSharedHistory()` 自动清理 |
| `photos-…` | `photos/` | ≤ 95 | 只剩 5 个位置时提前拒绝上传，并给出中文提示 |

`node scripts/check-budget.cjs` 会把这张表和真实代码对一遍：新增一条没有分片归属的写入路径、
把日期写回 `usage` 路径、拿掉归档上限，CI 都会直接失败。

分片后老数据搬过一次家（脚本保留备查，可安全重跑）：

```powershell
node --dns-result-order=ipv4first scripts/migrate-shards.mjs           # 预演，不写
node --dns-result-order=ipv4first scripts/migrate-shards.mjs --apply   # 执行
```

⚠️ 两个实测踩过的坑：写 MantleDB 时 POST **必须带** `Content-Type: application/json`，
少了它会拿到 500 Internal Server Error；本机到 mantledb.sh（Cloudflare）的 IPv6 不通，
所有直连脚本都建议加 `--dns-result-order=ipv4first`。

### 迁移到 Supabase（替代 MantleDB）

MantleDB 的两条硬顶（100 条 / 10000 次请求）和「口令摘要在公开命名空间可被离线爆破」这两件事，
只有换到真正的后端才能根治。仓库已经把迁移准备好，**但线上现在仍然跑 MantleDB**（`provider: "mantle"`）：

- `backend-supabase.js` — Supabase（PostgREST）适配器，接口与 MantleDB 版完全一致；
- `supabase/202610160001_class_hub_entries.sql` — 建表 + 条数/频率触发器 + RLS（幂等，可重复跑）；
- `supabase/202610160002_sports_photo_storage.sql` — 运动会照片的 Storage 桶 + RLS（**照片清晰化的关键**）；
- `scripts/migrate-to-supabase.mjs` — 把 MantleDB 的数据搬过去（默认只预演，`--apply` 才写）；
- `scripts/check-backend.cjs` — 守住「换后端只换适配器」这条约定（URL 形状、四种读写、错误语义）。

> **为什么照片要单独建桶**：`class_hub_entries` 把一张照片当成一条 JSON 记录，单条上限
> 256 KB（MantleDB 更只有 64 KB），所以照片只能压到 480~640 px，点开就糊。照片改存对象
> 存储后，记录里只留两个路径，网格读缩略图（约 13 KB）、点开才读原图（2048 px、0.2~0.8 MB），
> 清晰度和首屏流量一起解决。桶没建好时照片仍走内嵌模式，不会白屏，只是继续糊。

切换步骤（第 1、3 步需要你在浏览器里自己点）：

1. 打开 <https://supabase.com/dashboard>，用邮箱注册并新建项目；区域选 **Southeast Asia (Singapore)**（离国内最近）。
2. 左侧 **SQL Editor → New query**，把 `supabase/202610160001_class_hub_entries.sql` 整段粘贴后 Run。
   正常会看到自检结果 `entries = 0`、`policies = 4`。再开一个 New query，把
   `supabase/202610160002_sports_photo_storage.sql` 整段粘贴后 Run，会看到 `bucket = 1`、`policies = 3`。
3. **Project Settings → API** 里复制 `Project URL` 和 `anon public`，填进 `config.js` 的
   `supabaseUrl` / `supabaseAnonKey`（anon key 本来就是公开密钥，写在静态站里不算泄露）。
4. 导入数据（这一步不影响线上，只是往 Supabase 写一份副本）：

   ```powershell
   node --dns-result-order=ipv4first scripts/migrate-to-supabase.mjs           # 预演，只读
   node --dns-result-order=ipv4first scripts/migrate-to-supabase.mjs --apply   # 写入 + 回读校验
   ```

5. 把 `config.js` 的 `provider` 改成 `"supabase"`，跑 `node scripts/bump-version.mjs`，提交推送，
   然后打开线上页面把登录、发布、课表、运动会照片各走一遍。
6. 回退：把 `provider` 改回 `"mantle"` 再推一次就行 —— 迁移脚本**只读不删**，MantleDB 里的数据一条没动。

⚠️ 第一阶段（也就是现在这套 SQL）的权限与 MantleDB 时期**同级**：anon 可以读写整个 `banji-*` 分区，
换来的只是「更可靠的数据库 + 没有 100 条/10000 次的天花板」。真正的权限边界要等第二阶段接入
Supabase Auth（用 `auth.uid()` 收紧 RLS、把口令校验搬进 `security definer` 函数）之后才立得起来。

### 备份

MantleDB 不会替你备份，请定期自己导出一份：

```powershell
python scripts/backup-mantle.py
```

不带参数运行会从 `config.js` 读出**全部 5 个命名空间**，各导出一份
`backups/banji-backup-<命名空间>-<时间戳>.json`（数据是分片存放的，只备份主片等于丢掉 4/5）。
只想导其中一个时用老写法：`python scripts/backup-mantle.py <namespace> <输出文件>`。

导出文件里含同学的真实信息和口令摘要，**不要提交进 git，也不要外传**。

## 安全边界与已知限制

这一节是**如实说明**，不是免责话术。上手前请先读它：

- **没有服务端，所以没有真正的权限校验。** 管理员名单（`config.js` 的 `adminUsernames`）、
  班级隔离、发布额度、删除归属、身份审核，全部在浏览器里判断。
  知道命名空间的人可以直接调用 MantleDB 接口改写任何一条记录。
- **口令摘要放在公共命名空间里。** 摘要用 PBKDF2-SHA256（16 字节随机盐、12 万次迭代）计算，
  不会泄露明文，但可以被离线爆破。**请不要用你在别的网站用过的密码。**
- **匿名意见箱目前并非真正匿名**：提交时会带上作者 id 和访问者 id，只在界面上不显示。
  这一条正在改，改完之前请把它当作"署名但不对全班公示"来理解。
- **课表与个人数据是公开可读的**：知道 `schedules/<userId>` 就能读到对应课表。
- 因此现阶段的定位是**班级内部的小规模试用**，不要放敏感信息，也不要指望防得住有心人。
- **免费档有硬顶**：每个命名空间最多 100 条 entry、每 24 小时最多 10000 次请求
  （详见「存储分片」）。满了以后**新同学注册、发布事项、传照片都会失败**；
  客户端会提前提示「共享库已满」或「照片位快满了」，但真正解决要靠清理或迁移。
- 迁移到真正的后端（Supabase / 腾讯云 / 阿里云）是解决上述问题的正路，
  触发条件大致是：出现一次数据丢失、同学数超过 60、开始存任何敏感字段、需要审计或删除请求。
- **Supabase 第一阶段不等于安全**：搬过去之后，`provider: "supabase"` 的读写权限和 MantleDB 时期同级
  （anon 可读写 `banji-*` 分区），口令摘要同样可以被离线爆破。它解决的是「容量/限流天花板」和
  「数据库可靠性」；权限边界要等第二阶段接入 Supabase Auth 才算立起来。

## 部署

整个目录可直接上传到 GitHub Pages、Netlify、Vercel 或普通静态服务器。入口文件是 `index.html`，所有运行资源均使用相对路径。

改完 `app.js` / `styles.css` 后，记得把 `index.html` 里引用它们的 `?v=` 版本号一起改掉
（例如 `app.js?v=20261005`）。GitHub Pages 没法自定义响应头，默认只给约 10 分钟缓存，
不加版本号的话同学刷新页面还是会拿到旧脚本。

- 上传文件保存在当前浏览器的 IndexedDB 中（库名 `banji-shared-files`），不会上传到共享接口。
